# Behavioral checks for skill maintenance

Use when changing this skill's decision behavior. These are synthetic scenarios, not claims about a customer or the author's experience. Test actual answers and reference selection rather than headings or keyword matches.

Give an independent evaluator the current SKILL.md, a request below, and permission to read the skill's references. Keep this file's review criteria out of its prompt. Restrict the run to analysis and temporary artifacts; no customer contact, external mutations, or project implementation. Review the answer against the criteria afterward. Record failures and limits; a passing scenario does not prove all branches or real production behavior.

| Scenario to give the evaluator | Review criteria |
| --- | --- |
| A three-person team has 20 small-merchant pilots and 10,000 monthly support conversations, 70% about returns/exchanges. It wants fully automatic refunds and charging within six weeks. Inference is cheap; success, complaint, human cost, and authority data are unknown. Ask for business/product/architecture advice. | Distinguishes conversations from refundable cases; addresses payer, authority, domain rules, adoption and full handling cost; proposes a complete bounded slice and measurable next decision; preserves permissions, idempotency, reconciliation, and human recovery; invents no ROI or success baseline. |
| An established internal reporting tool has a stable 20-item configuration array, read once per build. There is no performance fault. Ask only whether to replace it with Map. | Gives a proportionate direct judgment grounded in lookup/maintenance semantics. Avoids a market study, unnecessary benchmarking, tests, or implementation work. |
| A B2B workflow product has 300 customers and six engineers. Two teams occasionally wait for each other's release; deployment is twice weekly. Capacity is unmeasured. A proposal asks for eight microservices for future growth. Ask for review and first delivery. | Examines the evidenced delivery bottleneck; compares modular monolith/selective extraction with the proposed split; accounts for data, operations and team cost; proposes a bounded useful slice, baseline, recovery and review trigger. |
| A GUI Agent's refund request times out and the remote effect is unknown. Product suggests immediate retry to improve success. Ask for execution boundaries, recovery, and validation. | Treats the outcome as uncertain, not failed; uses authoritative status, stable operation identity and verified remote idempotency; enforces authority outside the model; handles partial effects and manual reconciliation; tests through the formal entrypoint. |
| A pnpm project with existing customers wants mandatory global installation of its project-scoped CLI because docs become shorter. CI is unattended; targets are Windows and macOS. Ask for recommendation and verification scope. | Preserves project/lockfile authority, considers a thin optional launcher or package script, verifies non-TTY behavior and child-process evidence, and distinguishes platform acceptance. Does not reopen established product strategy. |
| A Node.js service's RSS is 200 MB at cold start and 800 MB after 24 hours. Ask whether this proves a leak and how to diagnose ongoing cost. | Requires comparable workload/lifecycle metrics, distinguishes heap/native retention and normal warmup, uses repeated lifecycle evidence and ownership analysis before micro-tuning, and states what remains unproven. |

On 2026-11-05, three independent GPT-6.1 Sol evaluators produced answers for two scenarios each. All six satisfied the scoped review criteria without an observed blocking behavior defect. The exercises checked reasoning, scope, and reference routing; no merchant trial, deployment, refund, CLI platform run, or memory experiment was executed. Raw evaluator output remained temporary. Re-run the affected cases after consequential changes; do not treat this result as a permanent quality guarantee.
