# Joyally Test Quality

测试的价值在于：产品行为或调用方依赖的契约发生可信的回归时，它能失败并指出问题。测试数量、覆盖率和写作顺序不能单独证明价值。审查时同时考虑保护范围、误报、执行概率和维护成本；证据不足就说明无法判断。

## 审查范围

先固定用户指定的 PR、目录、测试组或时间范围。读取这些测试及其运行入口，再按判断需要查实现、公开接口、相关需求或缺陷、现有同类测试、fixtures、mocks 和关键外部边界。对整个仓库的审查应分组抽样并说明覆盖范围，不把样本结论说成全量结论。

确认测试是否进入实际使用的验证命令，以及 skip、筛选条件和所需环境。未执行的测试不能为本次验证提供通过证据；可选的联网或设备测试单独标明。

## 判断每组测试

1. 写出它声称保护的行为，以及断言实际观察到的结果。检查预期值是否独立来自需求，而非照搬实现或 fixture 自身。
2. 给出一个具体、可信且有影响的回归：它发生时测试会失败吗？相反，行为仍正确但内部重构时，测试会不会无故失败？
3. 查相邻测试是否已覆盖同一失败机制，或是否有不同边界、失败路径使两者都值得保留。检查 mock 是否替换了本应验证的行为，快照是否有稳定的语义审阅方式。
4. 估计维护代价：实际运行耗时、非确定性、准备数据的复杂度、对内部结构的耦合，以及失败时定位问题的清晰度。没有测量就不声称节省了多少时间。

当重要结论取决于测试对某个缺陷是否敏感时，优先用已有的失败前证据或已知坏版本核对。必要的临时缺陷实验放在隔离副本中，保持被审查的测试不变；实验结束后只报告所试缺陷的结果，不把一次实验外推为全面保证。

## 处置

| 结论 | 依据与动作 |
| --- | --- |
| 保留 | 能观察到有意义的契约，可信回归会使其失败；即使测试内部细节，也有独特保护价值。 |
| 改写 | 保护目标有价值，但当前断言、mock、fixture 或运行方式让它漏报、误报或无法执行；改为观察实际行为。 |
| 删除 | 没有独立保护价值，或维护代价明显高于所保护的风险且不值得改写；先核对其他测试和兼容承诺。 |
| 补充 | 关键契约存在可信回归风险，现有测试未覆盖；只补最小且可稳定运行的场景。 |

仅检查文件、常量、选项或函数调用是否存在的测试，先确认这些是否属于对外承诺；不要仅因形式就删除。调用次数、顺序、权限拒绝、数据格式和配置也可能是契约。静态文案、原型和已移除功能通常不需新增回归测试，除非确有兼容或安全承诺。

对改动过的测试，比较改动前后实际能挡住的缺陷。删除旧断言前确认契约已变更、旧断言错误，或替代测试仍挡住相同风险。接口重命名不自动意味着原来的失败场景可以丢失。

## 交付边界

审查请求默认只给结论，不改测试。按影响排序说明每组的保留、改写、删除或补充建议，附测试位置、契约、具体回归和判断证据；没有证据时列出最小核对动作。优先给能缩短套件或提高缺陷发现率的少量改动，不为填满分类而凑建议。

用户要求实际治理时，先保留有价值的保护，再做最小修改并运行受影响的验证命令。若改正测试后暴露生产缺陷，保留失败并报告；测试清理本身不授权悄悄削弱断言或扩大为生产代码修复。分别报告通过、失败、跳过和未运行的范围。
